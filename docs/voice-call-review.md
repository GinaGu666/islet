## 不要动的

这些是对的，改的时候保持住：

- VPS 只签发一次性令牌；钥匙不出服务器；聊天正文、录音、生成稿都不经过 VPS。
- 只有完整播完的短句才写进聊天（`played`）；打断、挂断、切后台按 `turn` 丢弃迟到的音频。
- 通话提示挂在最后一条用户消息的 `_tail`，不进 system。
- 通话中不带工具。
- 空闲和回答期间释放麦克风（iOS 音频路由那几个修复，#97 #98）。

## 要改的，按对手感的影响排序

她的反馈是「有点像对讲机」。下面第 1、2 条是主要原因。

### 1. 句子之间有固定空档

**现状**：`voiceAnswer` 的 `enqueue` 把每句串在一条 `queue` 上，`voiceSpeak` 要等这一句**播完**才 resolve。所以下一句的「申请令牌 → 建 WebSocket → 等首包音频」是在上一句播完之后才开始的。每两句之间都白等这一整套。

**改法**：把「取音频」和「播放」分开。

- 一句进队就可以开始取音频（令牌、连接、收 PCM），收到的块先存着。
- 播放仍然严格按顺序：上一句的 `end` 之后才把下一句排上 AudioContext 时间线。
- 「已播」的边界不变：这一句的音频全部播完才 `played.push`。
- 提前量限制在 **1 句**。提前合成但没播的句子照样扣字符额度，她现在用的是免费档，打断时最多浪费一句。
- 打断 / 挂断 / 合成失败：关掉所有在取的连接，丢掉没播的缓冲。迟到的块仍按 `turn` 丢弃。

### 2. 按住之后要等一下才能说

**现状**：`voiceHold` 的顺序是 申请令牌 → 开麦克风 → 连识别。`c.node.port.onmessage` 在 `c.sttReady` 之前直接 `return`，这段时间的声音被丢掉。所以界面要她等到「正在听」再开口；松手太早还会走到「尚未开始收音，请重新按住」。

**改法**：按下就录，连上再补发。

- 按下后先开麦克风，`holding` 期间的 PCM 无论 `sttReady` 与否都先攒进缓冲。
- 收到 `session_started` 后把攒下的按现有分块大小补发，再继续实时发送。
- 缓冲设上限（建议约 15 秒的 16 kHz 采样），超了就按现在的方式提示重说，别无限涨。
- 松手时如果识别还没连上：不要判为失败。等连上、补发完、再 `commit`。只有连接真的失败才提示重按。
- 状态文字相应改掉：按下即可显示「正在听」。
- 注意保留 #97、#98 的约束：空闲和回答期间麦克风必须是释放的；录音前先切 `audioSession` 到 `auto`。

### 3. 短句没有并进下一句

方案里写了「太短的句子并进下一句」，现在的判断是：

```js
if (sentence.trim().length < 5 && sentence.length === pending.length) break;
```

它只在「短句后面还没有别的字」时等一下。下一个分片一到，`pending` 变长，短句就被单独送出去了。模拟结果：

```
分片：["嗯。", "我在", "呢。你今天", "过得怎么样？"]
现在：["嗯。", "我在呢。", "你今天过得怎么样？"]
期望：["嗯。我在呢。", "你今天过得怎么样？"]
```

每个单独送出的短句都要一次令牌 + 一次连接，还多一个停顿。

**改法**：短句不单独出队，继续往后并到下一个句末标点为止。流结束时剩下的照常冲出去（现有的 `enqueue(pending)`）。

### 4. 断句规则的几个缺口

切句用的是 `/^[\s\S]*?[。！？!?\n](?:[”」』]*)/`。

- **不认英文句号**。模拟：一段只用 `.` 的英文回复完全不会被切开，要等整段生成完才开始合成。她提过在练口语，如果通话里有英文回复，这条优先级要提到最前。
  加 `.` 时要避开小数和缩写：只在 `.` 后面跟着空白（或流结束）、且前一个字符不是数字时才算句末。
- **后引号会掉到下一句开头**。`。` 和 `”` 分在两个分片里时，前一句已经出队，下一句以 `”` 开头。
- **`……` `…` `；` `;` 不算断点**，带省略号的长句要等很久。建议加上。

**一个能同时解决前两点的简单规则**：只有当句末标点后面**至少还有一个字符**时才出队（流结束时的收尾除外）。这样能看见紧跟的后引号，也能判断 `.` 后面是不是空白。代价是多等一个分片，可以忽略。它和第 3 条的短句判断可以合成一处逻辑。

## 第 1 条合并后的遗留（PR #101）

第 1 条已由 PR #101 实现：提前一句取音频，播放顺序和「播完才算数」不变。复查时发现一处要补：

**提前取的那句失败，会打断正在播的这句。** `voiceAnswer` 的 `prepare()` 给每一句都挂了 `audio.played.catch(fail)`，包括还没轮到的那句（`ahead`）。它一失败，`fail` 就 `c.abort.abort()`，正在播的那句被取消、音源被停掉，也不进 `played`。改之前是这一句说完才报错。

容易碰到的情况：免费额度在一段回复中间用完。

**改法**：`ahead` 的失败先记着，不要立刻 `abort`。等当前句正常播完、`played.push` 之后，轮到它时再报错收尾。当前句自己的失败照旧立刻处理。补一条测试：当前句播放中、下一句预取失败 → 当前句完整播完并保存，然后才提示失败。

另：`tools/test_voice_call.cjs` 的测试要在有浏览器的环境里实际跑一遍再提交（它用 Playwright）。#101 提交时新加的一段覆盖了旧断言用的 `beforeFinalBuffers`，导致整份测试失败，合并前已修。

## 小项

- 松手之后如果一直等不到 `committed_transcript`，现在要等到 `recordTimer` 的 90 秒才超时。发出 `commit` 后可以换成一个短一些的计时（比如 15 秒）。
- 每句是独立连接、独立合成的，句与句之间语气会重新起头。方案文档里已记为待实测；第 1 条改完如果她觉得语气还是断，再考虑一次回答复用一条 TTS 连接。这是较大的改动，先不做。
- 用户消息在回答开始前就写进了聊天。如果一句都没播完就被打断，会留下一条没有回复的用户消息，下一轮是连续两条用户消息。这符合「以实际播放为准」，不用改，记一笔。

## 2026-11-12 施工备注

做了第 2、3、4 条、#101 遗留和提交后的短计时。和上面写的改法不一样、或者上面没写到的地方：

- **断句**（`voiceSplit`）：句末标点后面还有字才出队，流结束时收尾。新增断点 `…` `；` `;` 和英文 `.`。英文句号除了文档里说的两条（后面是空白、前面不是数字），还跳过了 `Mr. Dr. e.g.` 这类常见缩写和单个大写字母（姓名首字母）。连着的标点（`？！`、`。”`）跟前一句走。
- **短句合并**：中文仍是不到 5 个字算短。纯英文放宽到 12 个字符，否则 `Yeah.` `Okay.` 还是会单独送出去。
- **按下即录**：麦克风和识别令牌同时开始，不再先后排队。状态在麦克风真正打开后才显示「正在听」，之前是「正在打开麦克风…」——麦克风没开的那一小段确实录不到，不想让界面说谎。
- **太短的一按**：录到的声音不到 0.3 秒就松手，提示「按住稍久一点再说话」，不去连识别、不提交。
- **松手早于连接**：最多等 20 秒连上；连上后补发、提交。提交后等定稿最多 15 秒。按住总时长仍是 90 秒。
- **补发速度**：攒下的音频是一口气发出去的（每块 0.1 秒），比实时快。没有拿真实的 Scribe 验证过它接不接受这种发法；如果真机上「松手早于连接」那种情况识别不出来，先查这里。
- **预取失败**：除了不打断当前句，失败之后也不再往后预取，免得再浪费一句的额度。

`tools/test_voice_call.cjs` 补了：切句（短句合并、英文句号、小数和缩写、后引号、省略号和分号、编号）、预取失败时当前句完整播完并保存、按下即录的补发、松手早于连接、太短的一按、缓冲上限。在有 Chromium 的环境里实际跑过，通过。
