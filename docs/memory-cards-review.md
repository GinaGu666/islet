# 记忆卡 · 复查备注

> 2026-11-12，Fable 5.2 复查。对象：`main` 的 f128f3e（PR #104 之后）。
> 给下一位施工的人读。这里只写复查发现和改法，没有改任何代码。

## 看了什么、没看什么

- 读了 `index.html` 里「分层记忆库」整段（`MAX_CARDS` 到 `memRecall`）、`buildApiMessages` 里挂浮现块的地方、`distillMemory`、`tidyNow`、`recall` 工具、`memSnapshot`，以及 `server/server.js` 收卡片的部分。
- **没有**看过她本机的真实卡片，不知道现在有多少张、约定有多少条。下面关于「会不会碰到」的判断是从代码推出来的。
- 没有跑测试，没有改代码。

## 不要动的

这些是对的，改的时候保持住：

- 常驻层（L0）和浮现层（L2）各有固定字数预算（`MEM_CORE_BUDGET` 900、`MEM_RECALL_BUDGET` 600）。卡片再多，每轮成本不涨。
- L0 在 system 里，L2 挂在最后一条用户消息的 `_tail`，落在缓存断点之后。别把会变的东西挪进 system。
- 浮现是本地字面匹配，不调模型。
- 事件线（`prev`）：命中线上任意一张，整条线一起带出。
- 整理是「模型提案、她拍板」，置顶不参与。
- 提炼只增不改写；旧事有了后续就接一张 `FOLLOWUP`。
- `memSnapshot` 不带热度 `u`/`n`，否则每轮都会重推记忆库。

## 要改的，按影响排序

### 1. 到 500 张会静默、永久地删卡

**现状**：`addMemCard` 每次都调 `trimMemCards`。超过 `MAX_CARDS`（500）就删，顺序是：

1. 最旧的、从没被想起过（`n` 为空）的普通卡
2. 最旧的普通卡
3. 最旧的约定

置顶豁免。导入角色时也会走一次（搜 `c.cards.sort((a, b) => b.d - a.d); trimMemCards(c)`）。

问题：

- 没有提示，没有回收区，删了就没了。她最在意的事是东西不要丢。
- 「没被想起过」不等于不重要。只发生过一次、后来没再聊到的事最先被删。
- `trimMemCards` 直接 `splice`，不走 `memUnlinkCard`。删到事件线中间的卡，后面的卡 `prev` 悬空，一条线断成两截。
- 开了记忆库同步的角色，删掉的卡下一次推送时也会从服务器那份里消失。
- 上限不是为了省钱（预算固定），只是为了省空间。卡片在 `islet_companions`（localStorage）里，一张卡通常几十个字，500 张很小。服务器本来就收 2000 张（`body.cards.slice(0, 2000)`）。

**改法**：不删，改归档。

- `MAX_CARDS` 提到 2000，和服务器一致。
- 超出时把要淘汰的卡挪进归档，不删。淘汰顺序可以沿用现在的三轮。
- 归档放哪里要她同意再定。两个选项：
  - 留在 `islet_companions` 里另开一个数组（比如 `c.cardsArchived`）：简单，自动进备份，但继续占 localStorage。
  - 放 IndexedDB：不占 localStorage，但备份和导入都要跟着改。
- 归档的卡不进 L0、不参与 L2 浮现，但 `recall` 工具和面板搜索要能查到，面板里能看、能恢复。
- 淘汰前先 `memUnlinkCard`，线不断。
- 第一次发生归档时给她一个提示（toast 或记忆面板里一行字），说清挪了几张、在哪里看。
- 到 400 张左右在记忆面板提示可以点一次「整理记忆」。
- **备份格式保持向后兼容**：旧备份没有归档字段，按空处理；新备份多出的字段，旧版本导入时不能报错。照 `AGENT.md`「碰存储和备份要保守」：先写新的、读回校验，再动旧的。

### 2. 通话是英文，卡片是中文，互相勾不起来

**现状**：`memTokens` 把中文切成两字一组、英文按单词（`[a-z0-9]{2,}`）。`SYN_GROUPS` 只有中文。浮现和 `recall` 工具都用它。

她和 TA 通话用英文，打字用中文。通话走的也是 `buildApiMessages`，所以：

- 通话里说 "my dad"，写着「父亲」的卡不会浮现。通话时 L2 基本是空的，只剩 L0。
- 提炼提示词要求「用对话主要使用的语言」写卡。通话多的那段会提炼出英文卡，之后打字聊天时这些卡也勾不起来。
- 英文没有词形归并：`dogs` 配不上 `dog`。

**改法**，从便宜到贵：

- **提炼时统一卡片语言**。在 `distillMemory` 的提示词里固定用中文写卡（人名、作品名等专名保留原文）。这样卡片库只有一种语言。改之前问她一句：TA 的卡她想看中文还是英文。
- **同义词组加英文**。`SYN_GROUPS` 每组补上对应的英文词（`dad` `father`、`mom` `mother`、`work` `job`、`sleep` `insomnia`……），`memTokens` 里对英文单词也打组记号。现在只对汉字串做 `han.includes(w)`，英文词要另外匹配，注意按整词匹配，别让 `cat` 命中 `category`。
- 英文单词做最简单的归并（去掉结尾的 `s` / `es` / `ed` / `ing`），查询和卡片两边一致即可。
- 专名（人名、地名、宠物名）翻不了，靠上面两条解决不了。如果实测还是不够，再考虑通话时把最新一句用模型翻成中文关键词再召回——这会多一次请求和延迟，先不做。

### 3. 约定并不「保证常驻」

**现状**：`memCoreParts` 的顺序是 置顶 → 约定 → 其余新到旧，共用 900 字。超预算的行直接 `continue`。注释和 `MEM_CATS` 旁边写的是「约定类保证常驻注入」，实际不是：

- 置顶 + 约定超过 900 字后，排在后面的约定悄悄掉出去。因为它们没被 L0 收进 `ids`，还能靠 L2 被话题勾起，但不再是常驻。
- 同时最新的普通卡一张也挤不进 L0。
- 约定没有「已兑现」的出口。兑现了的约定一直占着位置，只能手动删或等整理。

**改法**：

- 给约定加一个「已兑现」状态（比如 `k.done = 1`）。已兑现的约定按普通事件卡对待，不再优先常驻。卡片编辑里加一个开关；提炼时如果新卡是某条约定的兑现（已有 `FOLLOWUP` 机制），可以顺手标上，这一步要小心误判，宁可不标。
- L0 给最新的普通卡留一块保底（比如预算的三分之一），不被置顶和约定挤光。
- 记忆面板显示常驻层的占用：置顶和约定用了多少字、有几条约定没放进去。她看得见才知道该整理。
- 注释改成和实际一致。
- 注意 `server/server.js` 第 134 行附近也按 `k.p || k.c === '约定'` 取常驻卡，加了「已兑现」要两边一致；`memSnapshot` 目前不带这个字段。

### 4. 热度算得太快，而且决定删卡顺序

**现状**：`memRecall` 每次把卡送进上下文就 `n++`、更新 `u`。它在 `buildApiMessages` 里每轮都跑，所以同一个话题连聊 10 轮，同一张卡 `n` 就涨 10。而加成在 5 次封顶（`Math.min(k.n || 0, 5) * 0.06`），几轮就满，区分不出真正常被想起的卡。

另外：

- `n` 是否为空决定第 1 条里的淘汰顺序。
- 热度是直接改在内存对象上的，`memRecall` 自己不存。要等别处调了 `saveCompanions()` 才落盘，中间关掉页面这几次就丢了。影响不大，记一笔。
- 重新生成、继续生成也会各算一次。

**改法**：同一张卡一个自然日最多算一次（比较 `u` 的日期）。面板上「想起 N 次」的含义跟着变成「在 N 天里被想起过」。旧数据不用迁移，偏大的 `n` 反正已经封顶。

### 5. 整理一次只能动一小部分

**现状**：`tidyNow` 把所有非置顶卡一次发给模型，要求最多 15 条动作，输出上限 2048 token。几百张卡时：输入很长，一次只能合并或删掉十几张，她要反复点。

**改法**：

- 分批：每批 80–100 张，按相关性聚在一起比按时间切更容易发现重复（可以复用 `cardTokens` 做粗聚类；简单起见先按分类 + 时间切也行）。
- 提案仍然汇总到同一个「整理提案」面板，她一次拍板。
- 保持「置顶不参与」「Prefer M over D」。
- 合并（M）时注意事件线：被合并掉的卡要走 `memUnlinkCard`，合并出的新卡接上原来的 `prev`。现状有没有处理没细看，改之前先确认 `applyTidy` 那段。

## 小项

- `memDup` 只按子串查重（长度超过 8 且一方包含另一方）。「喜欢喝拿铁」和「爱喝拿铁」算两张。靠提炼时给模型看旧卡 + 整理兜底，不用改，记一笔。
- 卡片少的时候（几十张），多数两字组合只出现在一两张卡里，权重都是满的，浮现容易偏吵。卡多了自然好转，不用改。
- `MEM_THREAD_MAX` = 6：一条线超过 6 张时只带开头和最新 5 张，中间的不带。符合设计。
